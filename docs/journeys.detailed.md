# Detailed journeys

Every journey in [journeys.md](journeys.md) cut into vertical slices of 1 to 3 days. Each slice
is end to end (API, screen, acceptance test) and ships on its own. Slices are listed in
dependency order: each one builds only on slices above it, so work can go straight down the
table. A slice ID is its root journey's number followed by the slice's position in that journey.

## Why this order

- **Foundations first.** Scaffolding, the shared design-system components (12–14), error screens, accounts and staff sign-in come before
  anything that needs a signed-in person. Roles and audit (15–16) land before the first staff
  change, so no admin action has to be retrofitted later.
- **Events before members can browse them.** Staff create and publish events (17–19) before
  members browse, view and register (20–25). Cancelling an event (26) waits until there are
  registrations it affects.
- **Profiles before messaging.** Profiles (29–31) come before chat, so a direct message can start
  from a member's profile (36). Home (37–38) waits for the events and unread counts it shows.
- **Applications before listings.** Members apply (42) and staff approve (43–44) before members
  can browse what was approved (45–48). The landing page's professionals section (51) waits
  for listings to exist.
- **Moderation before the dashboard.** Reports (52) produce flagged members, staff act on them
  (53–55), and the dashboard (56–57) shows the work those slices create.
- **Apply to be listed** (42) has no mock yet; one is needed before it starts.
