Pattern

Tables and lists

Tables are for staff comparing many records; lists are for members scanning a few. Both stay readable on a phone.

WCAG 2.2 AA
  • Overview
  • When to use
  • Structure
  • States
  • Responsive
  • Accessibility
  • Content
  • Do and don't
  • Sources

Overview

Use a table when people compare values across columns (admin events, members, services). Use a list or card grid when each item is read on its own (conversations, upcoming events, professionals).

When to use

  • Table: staff, 3+ comparable attributes, sorting or status scanning.
  • Event grid: members browsing events; the image and date matter.
  • Divided list (.mini-list, .list-divided): conversations, going list, people.
  • Description list: facts about one record.
  • Inbox split (.split--inbox): a list of items to work through beside the open one, when each needs reading and an answer (feedback). Rows are feedback rows.
  • Picker split (.split--picker, --picker-wide): a short list of records beside the chosen record, when there are a handful and staff work on one at a time (series, listing suggestions). The list is pick cards.
  • Builder and pick splits (.split--builder, .split--pick): the thing being made beside its side column (send card) or its result (Community Pick assets); choices inside are pick lists and event choices.

Filters sit above: tabs for status, chips for category, search on the right of the page head. Bulk actions are not in the mocks; add them only with a mock first.

Structure

Table: hidden caption, column headers with scope, the first column as the record's name plus a sub-line, numbers right-aligned in tabular figures, status as a status badge, row action last.

States

Lists and tables go loading (skeleton rows of the same shape), loaded, empty, no results (keep filters, echo the query) and error (retry in place, tabs stay). Rows show hover and focus; unread rows are bold and carry a dot with a text count, never colour alone. Long session lists (chat, members) render a window, not everything.

Responsive behaviour

  • Tables scroll horizontally inside .table-wrap; the page never scrolls sideways. .table--wide and .table--wider set a minimum width so columns don't crush.
  • Event grids go 1 → 2 → 3 columns; lists stay one column.
  • On phones, Messages shows the list or the thread, never both.
  • Inbox, picker, builder and pick splits are one column below 1024px, list (or form) first; the pick cards become a sideways scroller unless --stack. From 1024px the list column is fixed (17.5rem, 18.75rem or 21.25rem) and the record takes the rest.

Accessibility

  • Every table has a caption (visible or hidden) and scope on headers.
  • Row actions name their record: "Edit Easter Sunrise 5K" reads as "Edit Easter Sunrise 5K".
  • A scrolling .table-wrap is keyboard reachable (Tab then arrow keys) and labelled.
  • Empty cells say so: the em dash is aria-hidden and visually hidden text beside it reads "Not given".
  • Whole-row links are one <a> per row; no nested interactive elements.

Content

  • Column headers are short nouns in sentence case: "Event", "Registered".
  • Dates in tables are compact ("Apr 18 · 6:45 AM"); in lists, relative for today ("8:12 AM") and weekday within a week ("Mon").
  • Numbers use digits and a thin separator for fill: "142 / 200".
  • Home church is optional; show "—" when not given and never sort or filter members by faith details.
