# L2 - Detailed Requirements

Viewports: XS < 576 px, SM >= 576 px, MD >= 768 px, LG >= 992 px, XL >= 1200 px.

## L2-001: Landing page content
**Traces to:** L1-001

The landing page shall show the headline, the next three published events, the community and
professionals sections, the John 10:10 verse and calls to join and sign in.

**Acceptance Criteria:**
1. Given a visitor who is not signed in, when they open `/`, then the page shows the headline, "Join free", "Sign in" and the next three published events in date order.
2. Given fewer than three published upcoming events, when the landing page loads, then it shows only those events and no empty rows.
3. Given no published upcoming events, when the landing page loads, then the events list shows "No events posted yet. Check back soon."
4. Given a signed-in member, when they open `/`, then they are redirected to Home.

---

## L2-002: Landing page responsive layout
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given viewport XS, when the landing page loads, then hero text and image stack in one column, "Sign in" is reached from the header without horizontal scrolling, and no content overflows horizontally.
2. Given viewport LG or wider, when the landing page loads, then the hero shows text and image side by side and the events list sits beside the community and professionals sections.

---

## L2-003: Create a member account
**Traces to:** L1-002

A visitor joins with full name, email, password, optional home church and optional interests.

**Acceptance Criteria:**
1. Given valid name, email and a password of at least 8 characters, when the visitor submits Join, then an account is created, they are signed in and taken to Home.
2. Given an email already registered (compared case-insensitively), when the visitor submits Join, then no account is created and the email field shows "An account with this email already exists. Sign in instead?" with `aria-invalid="true"`.
3. Given a password shorter than 8 characters, a missing name or a malformed email, when the visitor submits, then the form names each invalid field and creates nothing.
4. Given the home church is blank, when the visitor submits valid details, then the account is created with no home church.
5. Given the form is submitting, when the visitor views the button, then it reads "Creating your profile…" and is disabled until the response arrives.
6. Given a name longer than 100 characters or a home church longer than 120, when submitted, then the server refuses it with code `field_too_long`.

---

## L2-004: Member sign-in and sign-out
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a registered member, when they sign in with the correct email and password, then a secure, HTTP-only, SameSite session cookie is set and they land on Home.
2. Given a wrong password or unknown email, when they sign in, then they see one generic message "Email or password is incorrect" that does not reveal which was wrong.
3. Given 5 failed sign-ins for one email within 15 minutes, when a sixth is attempted, then it is refused with code `too_many_attempts` and HTTP 429 until the window passes.
4. Given a suspended member, when they sign in with correct credentials, then sign-in is refused with code `account_suspended` and HTTP 403, and a message to contact the team.
5. Given a signed-in member, when they choose Sign out, then the session is ended on the server and they return to the landing page.
6. Given a visitor who is not signed in, when they open any member route, then they are redirected to sign-in and returned to that route after signing in; a return address that is not a path inside the member app opens Home instead.

---

## L2-005: View own profile
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given a signed-in member, when they open Profile, then it shows their name, initials avatar, city, join date, bio, home church, goals, interests and their upcoming registered events.
2. Given a member with no registered events, when they open Profile, then the events area shows an empty state with a link to Events.
3. Given a member opens another member's profile URL, when the page loads, then it shows only that member's public fields (name, initials, bio, interests) and never their email or home church unless that member chose to show it.

## L2-006: Edit own profile
**Traces to:** L1-003

Editing opens a dialog or a screen; there are no inline forms.

**Acceptance Criteria:**
1. Given a signed-in member, when they choose Edit profile, then a dialog opens with their current values.
2. Given valid changes, when they save, then the profile shows the new values and the dialog closes.
3. Given a bio over 300 characters, more than 5 goals or a goal over 80 characters, when they save, then the server refuses with code `field_too_long` or `too_many_goals` and nothing changes.
4. Given a member, when they choose whether their home church is visible to other members, then the choice defaults to hidden and is respected by L2-005 AC3.
5. Given a request to change another member's profile, when it reaches the API, then it is refused with HTTP 403 and nothing changes.

## L2-011: Register for an event
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given a free event with places left, when a member registers, then they are registered, going increases by one, and they join the event's group chat.
2. Given a full event, when a member tries to register, then it is refused with code `event_full` and the page shows "This event is full".
3. Given two members register for the last place at the same moment, when both requests are processed, then exactly one succeeds and the other receives `event_full`.
4. Given a member already registered, when they register again, then no second registration is created.
5. Given a paid event, when a member registers, then the registration is recorded as reserved and the page states how to pay; online payment is out of scope for this release.
6. Given a suspended member, when they try to register, then it is refused with code `account_suspended`.

## L2-016: Send and receive messages in real time
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given a member in a conversation, when they send a message of 1 to 2,000 characters, then it appears for every participant within 1 second without reloading.
2. Given an empty message or one over 2,000 characters, when sent, then it is refused with code `message_invalid` and the composer keeps the text.
3. Given a member who is not a participant, when they try to read or send in that conversation, then it is refused with code `not_a_participant`.
4. Given message text containing HTML or script, when displayed, then it is rendered as plain text.
5. Given the real-time connection drops, when it returns, then missed messages are fetched and the member sees a "Reconnecting…" status meanwhile.
6. Given a conversation with more than 50 messages, when opened, then the latest 50 load and earlier ones load on scrolling up; the client holds at most 200 in memory.
7. Given a member opens a conversation, when its messages show, then its unread count becomes zero.

## L2-030: Password storage and session security
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given any account, when its password is stored, then it is hashed with ASP.NET Core Identity's PBKDF2 hasher and never logged or returned.
2. Given session cookies, when set, then they are `Secure`, `HttpOnly`, `SameSite=Lax` or stricter, and use the `__Host-` prefix.
3. Given a state-changing request from another origin, when it arrives, then it is refused (antiforgery).
4. Given any response, when served, then it carries a Content-Security-Policy without `unsafe-inline` scripts, HSTS in production, `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`.

## L2-031: Authorization by ownership
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given any endpoint, when called without a session, then it returns 401 unless it is explicitly anonymous (landing data, join, sign-in).
2. Given a member, when they request another member's private data, registrations or conversations they are not part of, then the API returns 403 or 404 and no data.
3. Given an id in a URL, when it does not belong to the caller, then guessing ids reveals nothing (opaque ids, uniform 404).

## L2-032: Input validation and errors
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given any request body, when it fails validation, then the API returns 400 ProblemDetails with a `code` and field errors, and the screen shows a generic message.
2. Given an unexpected server error, when it occurs, then the response is a 500 ProblemDetails with no stack trace or internal detail.
3. Given user-supplied text, when rendered anywhere, then it is shown as text, never as HTML.
4. Given any error response (401, 403, 404, 500), when served, then its body is ProblemDetails with a `code` a client can branch on.

## L2-042: Continuous integration
**Traces to:** L1-016

Every push to `main` and every pull request against it shall run the frontend's lint, format
check, build of both apps within their budgets and Playwright behaviour specs, and the backend's
build with warnings as errors and its acceptance tests through the API, in one GitHub Actions run of under five minutes with
no retries.

**Acceptance Criteria:**
1. Given a push to `main` or a pull request against it, when CI runs, then it runs the frontend's lint, format check, build of both apps and Playwright behaviour specs on Chromium, and the backend's build with warnings as errors and its acceptance tests through the API (`dotnet test`).
2. Given a change that breaks any of those checks (a lint error, a format difference, a build or budget error, a failing spec or test), when CI runs, then the run fails at that check and names it; nothing is retried.
3. Given a change that passes every check, when CI runs, then the run is green in under five minutes, using cached npm packages, NuGet packages and the Playwright browser.
4. Given CI, when it runs, then it needs no secret and no real backend or database: the specs answer every request through the shared fixture and the backend tests use EF Core InMemory.

## L2-043: Error screens
**Traces to:** L1-015, L1-013

Either app shall answer a URL it does not know with a not-found screen and an unrecoverable
server error with a server-error screen, each in plain words with a way back, and the API shall
give every server error a reference a member can quote and an operator can find.

**Acceptance Criteria:**
1. Given either app, when a person opens a URL no route matches, then a lazily loaded not-found screen shows the heading "Page not found" in one `main` landmark, the document title is "Page not found · Christian Fitness" (member app) or "Page not found · Christian Fitness Admin" (admin app), and the URL stays as opened.
2. Given the not-found screen, when shown, then the member app offers "Go to home" (`/`) and "Browse events" (`/events`) and the admin app offers "Go to dashboard" (`/`) and "Manage events" (`/events`), each a link reachable by keyboard with a target of at least 44 × 44 px.
3. Given an unexpected server error, when the API answers with a 5xx ProblemDetails, then it carries a `reference` made of `CF-` and the first eight hexadecimal digits of the request's trace id in upper case (for example `CF-4BF92F35`); a 4xx ProblemDetails carries no `reference`.
4. Given a request from either app to the API that reads data (GET), when it answers 5xx, then the app shows the server-error screen in place of the current screen without changing the URL: the heading "Something went wrong", the title "Something went wrong · Christian Fitness" (or "· Christian Fitness Admin"), and the sentence "If it keeps happening, quote reference …" only when the response carries a well-formed reference.
5. Given a request that changes data (POST, PUT, PATCH or DELETE), a 4xx answer, or no answer, when it fails, then the server-error screen is not shown; the screen that sent the request handles the failure.
6. Given the server-error screen, when "Try again" is chosen, then the app loads the URL that failed again from the server, and "Go to home" (member app) or "Go to dashboard" (admin app) loads `/`; a return URL that is not a path inside the app is replaced by `/`.
7. Given an error screen, when it opens, then focus moves to its heading and the decorative code ("404", "500") is hidden from assistive technology.

## L2-044: Request a password reset link
**Traces to:** L1-002, L1-013

A member who has forgotten their password shall ask for a reset link by email from the Sign in
screen, and the answer shall never reveal whether an account has the email given.

**Acceptance Criteria:**
1. Given the Sign in screen, when a visitor chooses "Forgot your password?", then the Forgot password screen opens at `/forgot-password` with the heading "Reset your password", one Email field and "Send reset link".
2. Given the email of a registered member (compared case-insensitively, ignoring surrounding spaces), when it is submitted, then the API answers 202 with no body and sends one email to the account's address holding a single-use link to `/reset-password` that expires 30 minutes after the request; only a hash of the link's token is stored.
3. Given an email no account has, when it is submitted, then the API answers exactly as for a registered member (202, no body), sends no email, and the screen shows the same "Check your email" message.
4. Given the request is accepted, when the screen answers, then it shows "Check your email" with the email as typed, says the link expires in 30 minutes, offers "Back to sign in" and lets the member send it again.
5. Given a blank or malformed email, when submitted, then the screen sends nothing, shows a summary that links to the field and marks the field `aria-invalid="true"` with "Enter an email address like name@example.com"; the API refuses such a body with 400 and code `validation_failed`.
6. Given 3 reset emails sent for one account within an hour, when another is requested for it, then the API answers the same 202 and sends no email until the hour has passed.
7. Given the form is submitting, when the visitor views the button, then it reads "Sending…" and is disabled until the response arrives; given the server fails or does not answer, then the screen shows "We couldn't send the email" and keeps the email typed.
8. Given a reset request, when it is traced and logged, then no span, metric or log carries the email, the token or the link (L2-033 AC2).

## L2-045: Choose a new password
**Traces to:** L1-002, L1-013

A member who opens a valid, unexpired reset link shall set a new password once, which signs
them out everywhere.

**Acceptance Criteria:**
1. Given a reset link, when the member opens it, then `/reset-password` checks the link, showing "Checking your link…" while it waits, and then shows "Choose a new password", "For" the account's email, "New password" with "At least 8 characters", "Confirm new password" and "Save password"; the token is read from the link's fragment, sent only in a request body and removed from the address bar.
2. Given a link that has not been used and was requested less than 30 minutes ago, when the member saves a password of at least 8 characters typed the same in both fields, then the API answers 204 with no body, the new password signs in and the old one no longer does, and that link and every other unused link for the account stop working.
3. Given the password is saved, when the reset completes, then every session of the member ends on the server, the member is not signed in, and the screen shows "Password saved", says they were signed out on their other devices and offers "Sign in".
4. Given a link that is unknown, already used or requested 30 minutes ago or more, or no token at all, when it is checked or a password is saved with it, then the API refuses with 410 and code `reset_link_expired`, changes nothing, and the screen shows "This link has expired" with "Send a new link" (`/forgot-password`) and "Back to sign in".
5. Given the two passwords differ or the new one is shorter than 8 characters, when submitted, then the screen sends nothing, shows a summary that takes focus and links to each invalid field, and marks the field `aria-invalid="true"`: "Type the same password in both fields" on the confirm field (summary "Your passwords don't match"), "Use at least 8 characters" on the new one; the API refuses a password shorter than 8 characters with 400 and code `validation_failed`.

## L2-046: Two-step verification for staff
**Traces to:** L1-008, L1-013

Staff shall confirm every admin sign-in with a 6-digit code from an authenticator app (TOTP,
RFC 6238) after their password, so a password alone never opens the admin app.

**Acceptance Criteria:**
1. Given a staff account with two-step verification set up, when it signs in with correct credentials, then the API answers 202 with no body and no staff session, and the admin app opens "Enter your code" at `/sign-in/verify` with one Verification code field (`autocomplete="one-time-code"`, numeric keyboard) and "Verify".
2. Given the code screen within 5 minutes of the password step, when the authenticator's current code (or the one 30 seconds before or after it, spaces allowed) is submitted, then the staff session starts, the API answers the staff session and staff land on the Dashboard; a code that already opened a session is refused as wrong.
3. Given a wrong or malformed code, when it is submitted, then it is refused with code `invalid_code` and HTTP 401, the field is marked `aria-invalid="true"` with "That code doesn't match. Codes change every 30 seconds, so enter the newest one." and the code typed stays.
4. Given 5 wrong codes for one account within 15 minutes, when another code is submitted, then it is refused with code `too_many_attempts` and HTTP 429, right or wrong, the pending sign-in ends, and Staff sign in says to wait 15 minutes before signing in again.
5. Given more than 5 minutes since the password step, or no password step, when a code is submitted, then it is refused with code `two_step_expired` and HTTP 401, and Staff sign in asks staff to sign in again.
6. Given a staff account without two-step verification set up, when it signs in with correct credentials, then it is refused with code `two_step_not_set_up` and HTTP 403 and no session; an operator sets it up with `cf two-step <email>`, which prints the authenticator link once.
7. Given a code is being checked, when staff view the button, then it reads "Verifying…" and is disabled and the field holds still; given the server fails, then the field shows "We couldn't check your code. Try again in a moment." and keeps the code.
8. Given a code check, when it is traced and logged, then no span, metric or log carries the code, the authenticator secret or the pending sign-in's cookie (L2-033 AC2).
