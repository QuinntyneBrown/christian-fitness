# L2 - Detailed Requirements

Viewports: XS < 576 px, SM >= 576 px, MD >= 768 px, LG >= 992 px, XL >= 1200 px.

## L2-001: Landing page content
**Traces to:** L1-001

The landing page shall show the headline, the next three published events, the community and
professionals sections, the John 10:10 verse and calls to join and sign in.

**Acceptance Criteria:**
1. Given a visitor who is not signed in, when they open `/`, then the page shows the headline, "Join free", "Sign in" and the next three published events in date order.
2. Given fewer than three published upcoming events, when the landing page loads, then it shows only those events and no empty rows.
3. Given no published upcoming events, when the landing page loads, then the events list shows "No events posted yet. Check back soon."
4. Given a signed-in member, when they open `/`, then they are redirected to Home.

---

## L2-002: Landing page responsive layout
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given viewport XS, when the landing page loads, then hero text and image stack in one column, "Sign in" is reached from the header without horizontal scrolling, and no content overflows horizontally.
2. Given viewport LG or wider, when the landing page loads, then the hero shows text and image side by side and the events list sits beside the community and professionals sections.

---

## L2-003: Create a member account
**Traces to:** L1-002

A visitor joins with full name, email, password, optional home church and optional interests.

**Acceptance Criteria:**
1. Given valid name, email and a password of at least 8 characters, when the visitor submits Join, then an account is created, they are signed in and taken to Home.
2. Given an email already registered (compared case-insensitively), when the visitor submits Join, then no account is created and the email field shows "An account with this email already exists. Sign in instead?" with `aria-invalid="true"`.
3. Given a password shorter than 8 characters, a missing name or a malformed email, when the visitor submits, then the form names each invalid field and creates nothing.
4. Given the home church is blank, when the visitor submits valid details, then the account is created with no home church.
5. Given the form is submitting, when the visitor views the button, then it reads "Creating your profile…" and is disabled until the response arrives.
6. Given a name longer than 100 characters or a home church longer than 120, when submitted, then the server refuses it with code `field_too_long`.

---

## L2-004: Member sign-in and sign-out
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a registered member, when they sign in with the correct email and password, then a secure, HTTP-only, SameSite session cookie is set and they land on Home.
2. Given a wrong password or unknown email, when they sign in, then they see one generic message "Email or password is incorrect" that does not reveal which was wrong.
3. Given 5 failed sign-ins for one email within 15 minutes, when a sixth is attempted, then it is refused with code `too_many_attempts` and HTTP 429 until the window passes.
4. Given a suspended member, when they sign in with correct credentials, then sign-in is refused with code `account_suspended` and a message to contact the team.
5. Given a signed-in member, when they choose Sign out, then the session is ended on the server and they return to the landing page.
6. Given a visitor who is not signed in, when they open any member route, then they are redirected to sign-in and returned to that route after signing in.

---

## L2-005: View own profile
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given a signed-in member, when they open Profile, then it shows their name, initials avatar, city, join date, bio, home church, goals, interests and their upcoming registered events.
2. Given a member with no registered events, when they open Profile, then the events area shows an empty state with a link to Events.
3. Given a member opens another member's profile URL, when the page loads, then it shows only that member's public fields (name, initials, bio, interests) and never their email or home church unless that member chose to show it.

---

## L2-006: Edit own profile
**Traces to:** L1-003

Editing opens a dialog or a screen; there are no inline forms.

**Acceptance Criteria:**
1. Given a signed-in member, when they choose Edit profile, then a dialog opens with their current values.
2. Given valid changes, when they save, then the profile shows the new values and the dialog closes.
3. Given a bio over 300 characters, more than 5 goals or a goal over 80 characters, when they save, then the server refuses with code `field_too_long` or `too_many_goals` and nothing changes.
4. Given a member, when they choose whether their home church is visible to other members, then the choice defaults to hidden and is respected by L2-005 AC3.
5. Given a request to change another member's profile, when it reaches the API, then it is refused with HTTP 403 and nothing changes.

---

## L2-007: Member home
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a signed-in member, when they open Home, then it greets them by first name and shows their next registered event, up to three suggested events matching their interests and their unread message count.
2. Given no registered events, when Home loads, then the next-event area invites them to browse Events.
3. Given the home data request fails, when Home loads, then a generic error with Try again is shown and Try again reloads it.

---

## L2-008: Member app navigation
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given viewport MD or wider, when a member is in the app, then a header shows Home, Events, Services, Messages and Profile with `aria-current="page"` on the current one.
2. Given viewport XS or SM, when a member is in the app, then the same destinations appear in a bottom bar with targets of at least 44 × 44 px.
3. Given unread messages, when the member views navigation, then Messages shows the unread count as text, not colour alone.

---

## L2-009: Browse and filter events
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given published upcoming events, when a member opens Events, then they are listed in date order with date, title, time, place, price and going/capacity.
2. Given a category filter (Run, Workout, Basketball, Mobility, Workshop, Retreat), when the member selects one, then only that category's events show and the filter button has `aria-pressed="true"`.
3. Given a filter with no matching events, when applied, then a no-results message with a Clear filter action is shown.
4. Given cancelled, draft or past events, when Events loads, then they are not listed.
5. Given more than 20 events, when the member scrolls to the end, then the next page of 20 loads.

---

## L2-010: Event detail
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given a published event, when a member opens it, then it shows image, title, category, date and time, place and area, price, summary, going/capacity and the registration action.
2. Given an event id that does not exist or is not published, when opened, then a not-found view is shown.
3. Given the member is registered, when they view the event, then it shows "You're going" and a link to the event's group chat.

---

## L2-011: Register for an event
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given a free event with places left, when a member registers, then they are registered, going increases by one, and they join the event's group chat.
2. Given a full event, when a member tries to register, then it is refused with code `event_full` and the page shows "This event is full".
3. Given two members register for the last place at the same moment, when both requests are processed, then exactly one succeeds and the other receives `event_full`.
4. Given a member already registered, when they register again, then no second registration is created.
5. Given a paid event, when a member registers, then the registration is recorded as reserved and the page states how to pay; online payment is out of scope for this release.
6. Given a suspended member, when they try to register, then it is refused with code `account_suspended`.

---

## L2-012: Cancel a registration
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given a registered member before the event starts, when they confirm Cancel registration in a dialog, then the registration is removed, going decreases by one and they leave the group chat.
2. Given the event has started, when they try to cancel, then it is refused with code `event_started`.

## L2-013: Browse services
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given published listings, when a member opens Services, then each shows name, role, where, price and avatar or photo.
2. Given a category (All, Training, Nutrition, Physio, Coaching, Counselling), when selected, then only matching listings show with `aria-pressed="true"` on the category.
3. Given a listing is selected, when viewport is LG or wider, then its detail (credentials, about, verified badge, contact action) shows beside the list with `aria-current="true"` on the row.
4. Given viewport below LG, when a listing is selected, then its detail opens as its own screen with a back action.
5. Given a listing that staff removed, when Services loads, then it is not shown.

## L2-014: Contact a professional
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given a listing with a linked professional account, when a member chooses Message, then a direct conversation with that professional opens.
2. Given a listing without a linked account, when the member chooses Contact, then the professional's published contact link opens; no contact details are shown until the member chooses it.

## L2-015: Conversation list
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given a member, when they open Messages, then their conversations are listed newest first with name, initials, last message, time and unread count; group chats show member count.
2. Given no conversations, when Messages loads, then an empty state links to Events.
3. Given viewport LG or wider, when a conversation is selected, then it shows beside the list; below LG, it opens as its own screen.

---

## L2-016: Send and receive messages in real time
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given a member in a conversation, when they send a message of 1 to 2,000 characters, then it appears for every participant within 1 second without reloading.
2. Given an empty message or one over 2,000 characters, when sent, then it is refused with code `message_invalid` and the composer keeps the text.
3. Given a member who is not a participant, when they try to read or send in that conversation, then it is refused with code `not_a_participant`.
4. Given message text containing HTML or script, when displayed, then it is rendered as plain text.
5. Given the real-time connection drops, when it returns, then missed messages are fetched and the member sees a "Reconnecting…" status meanwhile.
6. Given a conversation with more than 50 messages, when opened, then the latest 50 load and earlier ones load on scrolling up; the client holds at most 200 in memory.
7. Given a member opens a conversation, when its messages show, then its unread count becomes zero.

---

## L2-017: Report a message or member
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given a message from another member, when a member reports it with a reason, then the sender is Flagged for staff review and the reporter sees confirmation.
2. Given a member reports the same message twice, when the second report is sent, then no duplicate report is created.

---

## L2-018: Admin sign-in
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given a staff account, when it signs in to the admin app with correct credentials, then it lands on the Dashboard.
2. Given a member account without a staff role, when it signs in to the admin app, then it is refused with code `not_staff` and HTTP 403.
3. Given wrong credentials, when signing in, then one generic message is shown, and the L2-004 AC3 lockout applies.
4. Given a request to any admin endpoint without a staff session, when it arrives, then it is refused with HTTP 401 or 403 and no data is returned.
5. Given an admin session idle for 30 minutes, when the next request arrives, then the session has expired and the user must sign in again.

---

## L2-019: Staff roles
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given staff roles Admin and Moderator, when a Moderator uses the admin app, then they can moderate members but cannot manage events or services (HTTP 403).
2. Given an Admin, when they use the admin app, then every admin action is allowed.
3. Given any staff action that changes data, when it succeeds, then an audit entry records who, what, which record and when, without personal data in telemetry.

## L2-022: Create and edit events
**Traces to:** L1-010

**Acceptance Criteria:**
1. Given an Admin, when they create an event with title, category, start date and time, place, area, price, capacity, image and summary, then it is saved as a draft.
2. Given a missing required field, capacity below 1 or above 10,000, a start in the past or a summary over 1,000 characters, when saved, then the server refuses with a field-specific `code` and saves nothing.
3. Given an event with registrations, when an Admin lowers capacity below the number going, then it is refused with code `capacity_below_going`.
4. Given an uploaded image, when it is not JPEG, PNG or WebP or exceeds 5 MB, then it is refused with code `image_invalid`.

2. Given a search term, when entered, then the list shows members whose name or email contains it, case-insensitively.

## L2-029: Flag, suspend and reinstate members
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given an Active member, when staff flag them with a note, then their status becomes Flagged and the note is shown on their row.
2. Given an Active or Flagged member, when staff suspend them with a note and confirmation, then their status becomes Suspended, their sessions end and L2-004 AC4 and L2-011 AC6 apply.
3. Given a Flagged or Suspended member, when staff reinstate them, then their status becomes Active.
4. Given staff try to suspend their own account, when submitted, then it is refused with code `cannot_moderate_self`.

---

## L2-030: Password storage and session security
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given any account, when its password is stored, then it is hashed with ASP.NET Core Identity's PBKDF2 hasher and never logged or returned.
2. Given session cookies, when set, then they are `Secure`, `HttpOnly`, `SameSite=Lax` or stricter, and use the `__Host-` prefix.
3. Given a state-changing request from another origin, when it arrives, then it is refused (antiforgery).
4. Given any response, when served, then it carries a Content-Security-Policy without `unsafe-inline` scripts, HSTS in production, `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`.

---

## L2-031: Authorization by ownership
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given any endpoint, when called without a session, then it returns 401 unless it is explicitly anonymous (landing data, join, sign-in).
2. Given a member, when they request another member's private data, registrations or conversations they are not part of, then the API returns 403 or 404 and no data.
3. Given an id in a URL, when it does not belong to the caller, then guessing ids reveals nothing (opaque ids, uniform 404).

---

## L2-032: Input validation and errors
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given any request body, when it fails validation, then the API returns 400 ProblemDetails with a `code` and field errors, and the screen shows a generic message.
2. Given an unexpected server error, when it occurs, then the response is a 500 ProblemDetails with no stack trace or internal detail.
3. Given user-supplied text, when rendered anywhere, then it is shown as text, never as HTML.
4. Given any error response (401, 403, 404, 500), when served, then its body is ProblemDetails with a `code` a client can branch on.

---

## L2-033: Personal and faith data protection
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given home church and faith details, when a member joins, then they are optional.
2. Given any log, metric or span, when emitted, then it contains no email, name, home church, message text, token, query string or body.
3. Given a member, when they request deletion of their account, then their profile, registrations and authored messages are erased or anonymised within 30 days and they are signed out.
4. Given a member, when they request their data, then they receive an export of their profile, registrations and messages.

---

## L2-034: Rate limiting
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given more than 30 messages from one member in one minute, when the next is sent, then it is refused with code `rate_limited`.
2. Given more than 5 account creations from one IP address in one hour, when the next is attempted, then it is refused with HTTP 429.

---

## L2-035: Load performance
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given each app's production build, when built, then its initial JavaScript is at most 250 kB raw and the build fails beyond the `angular.json` error budget.
2. Given every route, when built, then it is lazy-loaded and not part of the initial chunk.
3. Given a mid-range phone on a 4G profile, when the landing page loads, then Largest Contentful Paint is under 2.5 s and Cumulative Layout Shift under 0.1.

---

## L2-036: API performance
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given normal load of 200 concurrent members, when list endpoints (events, services, conversations, members) are called, then 95% respond within 300 ms.
2. Given list endpoints, when called, then they are paged and never return more than 50 items per page.

---

## L2-037: Long-session stability
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given a member moves between screens 50 times, when the heap is measured after garbage collection, then it returns to within 10% of its level after the first visit.
2. Given a screen is left, when it is destroyed, then its subscriptions, timers, listeners and real-time handlers are released.

---

## L2-038: Accessibility
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given any screen, when checked with axe, then it has no WCAG 2.2 A or AA violations.
2. Given any interaction, when performed by keyboard only, then it is reachable in a logical order with a visible focus indicator.
3. Given any state (selected, invalid, unread, status), when shown, then it is not conveyed by colour alone.
4. Given text and controls, when measured, then text contrast is at least 4.5:1 and touch targets at least 44 × 44 px.
5. Given a user who prefers reduced motion, when they use the apps, then non-essential animation is disabled.
6. Given any screen of either app, when it loads, then the document title names the app ("Christian Fitness" in the member app, "Christian Fitness Admin" in the admin app) and the screen's content sits in one `main` landmark.

---

## L2-039: Responsive behaviour across viewports
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given each screen of both apps, when viewed at 375, 576, 768, 992 and 1440 px wide, then nothing overflows horizontally and no content is clipped.
2. Given list-and-detail screens (Services, Messages), when below LG, then list and detail are separate screens; at LG and above, they sit side by side.
3. Given forms, when viewed at XS, then fields span the full width and the primary action stays visible.

---

## L2-040: Telemetry and health
**Traces to:** L1-016

**Acceptance Criteria:**
1. Given the API, when it handles requests, then it emits OpenTelemetry traces and metrics with the route template, status and duration only.
2. Given a health endpoint, when called anonymously, then it reports liveness and readiness (database reachable) without internal detail.

---

## L2-041: Deployment and migrations
**Traces to:** L1-016

**Acceptance Criteria:**
1. Given a new release, when the API starts, then it does not apply migrations; a documented CLI command applies them.
2. Given seed data, when the seed command runs twice, then the second run changes nothing.
3. Given a setting a deployed system needs, when it is added, then it is documented in the same change.
